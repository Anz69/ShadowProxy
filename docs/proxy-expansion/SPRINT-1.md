# SPRINT 1 — Аудит, фиксы, Mango на гейтвей, скорость пакета

> **КРИТИЧНО, делаем первым.** Сначала прочитать `00-АРХИТЕКТУРА-И-ГЕЙТВЕЙ.md`.
> Состав (ТЗ п.9): 1) аудит и фиксы (п.8), 2) возврат Mango на гейтвей (п.6),
> 3) скорость создания пакета (п.7.3).
>
> Все три задачи завязаны на одну первопричину: **система синхронно ходит в API
> апстрима при покупке/триале и держит баланс по снапшотам апстрима**. Лечим — и
> 7.3, и 8.1, и 8.2 уходят вместе.

---

## 1.1. Первопричина (что нашли в коде)

1. **`@OnEvent('user.distribute_traffic')` в `mango-proxy.provider.ts`** при покупке/триале
   синхронно зовёт `POST /add_user_flow` (доливка трафика на суб-аккаунт Mango).
   Внутри ещё `sleep(2000)`, ретраи с `sleep(3000)`, recovery-флоу с пере-созданием.
   Если Mango тормозит/недоступен — запрос висит, вебхук-транзакция уходит в таймаут
   (`payments.service.ts`, `$transaction … {timeout:120000}`).
2. **Триал** (`user.service.ts → getTrial`, ~376–442) точно так же `await emitAsync(...)`
   на те же события → висит на Mango/PE API. Отсюда «Попробуйте через 15 минут».
3. **Баланс держим по снапшотам апстрима** (`user.premiumTrafficLeft`,
   `proxyEmpireResiUsedSnapshot`, …) + крон `updateUserBalances()` (раз в минуту тянет
   `/user_info`). Снапшот устаревает → **юзер видит трафик, а прокси не пускают**
   (или наоборот). Это баг 8.1.

**Решение:** баланс и подсчёт — **только наши** (через гейтвей → `TrafficLog`), при
покупке в апстрим **не ходим**.

## 1.2. ЗАДАЧА A — Возврат Mango на гейтвей (ТЗ п.6)

### Шаг 1. Фича-флаг (обязателен по ТЗ — чтобы можно было быстро откатиться)

`.env` / `@nestjs/config`:
```env
MANGO_MODE=gateway          # gateway | api
```
Хелпер в `mango-proxy.provider.ts`:
```ts
private isGatewayMode() { return this.config.get('MANGO_MODE','gateway') === 'gateway'; }
```
**Старый код API НЕ удаляем** — оборачиваем в `if (!isGatewayMode())`.

### Шаг 2. Отключить прямые вызовы API при покупке/триале (в gateway-режиме)

В `mango-proxy.provider.ts`:
- `@OnEvent('user.distribute_traffic')` (доливка `/add_user_flow`): в начале
  ```ts
  if (this.isGatewayMode()) return true; // баланс ведём у себя, апстрим не трогаем
  ```
- `@OnEvent('proxy.create_account')` (`/create_user`, `/add_proxy_account`):
  суб-аккаунт Mango всё ещё нужен как апстрим-креды для гейтвея, **но не на горячем пути
  покупки**. Вынести в ленивое создание (см. Задача C, «ленивый провижининг»).
- `@Cron(EVERY_MINUTE) updateUserBalances()` (`/user_info`):
  ```ts
  if (this.isGatewayMode()) return; // остаток считаем по TrafficLog, не из Mango
  ```

### Шаг 3. Маршрутизировать Mango через гейтвей

Сейчас для Mango (`RESIDENT_PREMIUM`) прокси отдаётся как «прямой провайдер»
(`serverHost=null`). Делаем как у `IPV6_GB`/`MOBILE_GB`:

В `proxy.service.ts` (выдача `RESIDENT_PREMIUM`) / `package.service.ts`
(`generatePackageProxy`) в gateway-режиме:
1. `providerProxy = await mangoProxyProvider.createProxy(country, …, rotationTime, …)`
   — берём **апстрим-строку** Mango (`username/password/host/port`).
2. Строим клиентские креды: `buildProxyLogin(packageId, providerUsername)` + `generatePasswordV2(...)`.
3. `serverHost = await proxyServerService.getServerForProxy()`.
4. Пишем `Proxy{ host/port/username/password=апстрим, userPort:10000, userLogin, userPassword, serverHost, type:'RESIDENT_PREMIUM', … }`.
5. `nodeService.createProxy([...], region)` → `POST /add-port` на гейтвей:
   ```json
   { "login":"package-…-user-…", "password":"…", "port":10000, "user_id":"…",
     "proxy_host":"<mango host>", "proxy_port":<mango port>,
     "proxy_username":"<полная mango-строка с session/sessTime>", "proxy_password":"<mango pass>" }
   ```
6. Юзеру отдаём `serverHost:10000` + `userLogin/userPassword`.

### Шаг 4. Что улучшить против «как было» (ТЗ п.6)

- Скорость гейтвея — см. спринт 2 (п.7.2).
- Стабильность подсчёта — счёт строго на гейтвее (`TrafficLog`), никаких параллельных
  источников истины.
- Логирование — на гейтвее логировать ошибки апстрим-CONNECT (код ответа), в CORE —
  ошибки `/api/proxy-node/traffic` и блокировок.

**Acceptance:** Mango-прокси работают через `serverHost:10000`; при `MANGO_MODE=api`
поведение откатывается к старому; покупка Mango-пакета не ходит в Mango API.

## 1.3. ЗАДАЧА B — Баланс/подсчёт только у нас + фикс 8.1

### Источник истины = TrafficLog (гейтвей)

- Остаток = `куплено_байт (наш баланс) − Σ TrafficLog(inBytes+outBytes) по userPackage`.
  (или ведём `usedBytes` инкрементом при приёме батча — но один источник).
- Приём батча: `proxy-node` контроллер `POST /api/proxy-node/traffic` —
  на каждый `log` находим `userPackage` по логину, `upsert` `TrafficLog(date,hour) += Δ`,
  пересчитываем остаток.
- **Порог блокировки:** при приёме батча, если остаток ≤ 0 → `POST /block-login {login}`
  на гейтвей того сервера (`server_id`). При пополнении/новом пакете → `/add-port`
  (сбросит `Blocked`).

### Фикс 8.1 «трафик есть, а прокси не работают»

- Убрать зависимость от снапшотов апстрима для НАШИХ типов и Mango
  (для ProxyEmpire-типов — **не трогаем**, они остаются как есть).
- Гейтвей не должен резать коннект, пока CORE не прислал `block-login`. Проверить, что
  блокировка ставится **только** по нашему расчёту, а не по ответу апстрима.
- Гонка «купил → старый снапшот»: при покупке в gateway-режиме снапшоты апстрима не
  участвуют, баланс растёт атомарно в нашей БД.

**Acceptance:** при положительном остатке прокси работают; блок ровно в 0; расхождение
баланса (наш счёт vs реальный трафик) в нагрузочном тесте < 1–2%.

## 1.4. ЗАДАЧА C — Скорость создания пакета (ТЗ п.7.3 / 8.2)

### Принцип: покупка/триал = быстрые операции в нашей БД. Апстрим — вне горячего пути.

**Было:** webhook/триал `await emitAsync('proxy.create_account')` + `await emitAsync('user.distribute_traffic')` → блок на Mango/PE API (секунды–минуты) → «через 15 минут».

**Стало:**
1. **Покупка** (`payments.service.ts → processPaidOrder`, case `package`):
   - в транзакции: создать/обновить `UserPackage`, **прибавить ГБ к балансу** в нашей БД,
     отметить оплату. Всё. Без внешних API. Транзакция закрывается за мс.
   - провижининг апстрим-аккаунта (если нужен суб-аккаунт Mango как апстрим-креды) —
     **в фон** (очередь/`@nestjs/schedule` воркер или BullMQ), идемпотентно, с ретраями.
2. **Триал** (`getTrial`): то же — записать триальные ГБ в баланс и вернуть успех сразу.
   Никаких синхронных `await` к апстриму.
3. **Ленивый провижининг суб-аккаунта Mango** (если он реально нужен для апстрим-кредов):
   создавать при ПЕРВОЙ генерации прокси, а не при покупке; кэшировать `premiumUsername`.
   В gateway-режиме апстрим-креды Mango общие/пулевые — суб-аккаунт на пользователя при
   покупке может быть вообще не нужен (уточнить у Mango-интеграции).
4. **Чёткая ошибка вместо «15 минут»:** если фоновый провижининг не завершился за 30с —
   показывать понятный статус «готовим, обновите через минуту», а не «через 15 минут»;
   пакет при этом уже создан и виден.

### Где править
- `payments.service.ts` — убрать тяжёлые `await emitAsync(...)` из горячего пути,
  оставить лёгкую запись + поставить задачу в фон.
- `user.service.ts:getTrial` — то же.
- Новый воркер `proxy-provisioning` (очередь) — идемпотентное создание апстрим-аккаунтов
  с ретраями и логами.

**Acceptance:** пакет/триал создаётся за < 3с (цель ТЗ — секунды); сообщения «через 15 минут»
нет; если апстрим лёг — пакет всё равно создан, баланс начислен, ошибка понятная.

## 1.5. ЗАДАЧА D — Аудит (ТЗ п.8, дополнительно)

Проверить и зафиксировать:
- **Одновременные подключения:** нагрузочный тест гейтвея (много логинов, параллельные коннекты).
- **Корректность подсчёта:** сверка переданных байт vs `TrafficLog` (расхождение < 1–2%).
- **Стабильность гейтвея под нагрузкой:** CPU/RAM, нет утечек (`countingConn`/`connMgr` чистятся в `defer Remove`).
- **Зависшие соединения:** таймауты на dial апстрима уже есть (30с) — проверить idle-таймауты.
- **Отказ апстрима:** что видит юзер, если `eu-isp.flashproxy.io` недоступен (CONNECT != 2xx) —
  гейтвей должен вернуть понятную ошибку и залогировать, не «вешать» коннект.
- **Логи:** добавить структурные логи на гейтвее (ошибки апстрима, блокировки) и в CORE
  (приём трафика, провижининг).

**Метрики ДО/ПОСЛЕ** зафиксировать в `docs/operations.md` (есть такой файл).
