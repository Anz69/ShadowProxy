# 00. Архитектура системы и прокси-гейтвей

> Базовый документ. Прочитать **до** спринтов. Объясняет, как устроена связка
> «бэкенд ↔ гейтвей ↔ апстрим», как считается трафик и как добавляются новые
> типы прокси. Спринты 1–3 ссылаются на этот документ.

---

## 0.1. Из чего состоит система

| Компонент | Стек | Путь | Роль |
|-----------|------|------|------|
| **Бэкенд (CORE)** | NestJS + Prisma (TS) | `backend/` | Биллинг, генерация прокси, БД, API для фронта и для гейтвея |
| **Прокси-гейтвей (agent)** | Go | `proxy-server-code/src/proxy-agent/` | Принимает клиента, проксирует в апстрим, **считает трафик**, блокирует при исчерпании |
| **Фронт** | Next.js 15 / React 19 | `frontend/` | ЛК, генерация прокси, выбор гео/ротации |
| **Апстримы** | внешние | — | `*.flashproxy.io`, Mango, ProxyEmpire — реальные источники IP |

Гейтвеев может быть несколько (по серверам/регионам), у каждого свой `server-id`.

---

## 0.2. Золотые правила (из ТЗ — действуют для ВСЕХ «обычных» типов)

1. **Трафик считаем ТОЛЬКО у себя** — на гейтвее. Не дёргаем API апстрима ради баланса.
2. **При покупке пакета НЕ ходим в API апстрима.** Просто пишем в нашу БД, сколько ГБ доступно.
3. **Гейтвей при прокидывании считает байты** и шлёт их в CORE (`POST /api/proxy-node/traffic`).
4. **Кончился трафик → CORE говорит гейтвею заблокировать логин** (`POST /block-login`), гейтвей рвёт коннекты.
5. **SESSION_ID для ротации по тайму генерим у себя**, кладём в upstream-строку. Пользователю его «как есть» не отдаём.
6. **Пользователь видит только НАШ гейтвей** (`serverHost:10000` + логин `package-…`). Апстрим (`flashproxy.io`, Mango) от него скрыт.

> **Premium Residential и Premium Mobile (ProxyEmpire) не трогаем** — они работают как сейчас (через прямой API). Новые типы и Mango — через гейтвей.

## 0.3. Поток данных end-to-end

```
                ┌─────────── ПОКУПКА / ТРИАЛ ───────────┐
ПОЛЬЗОВАТЕЛЬ ──▶ Next.js ──▶ CORE (NestJS)
                              │  1. пишет в БД: userPackage + баланс ГБ
                              │     (НИКАКИХ вызовов API апстрима!)
                              │  2. генерит прокси:
                              │       providerUsername = build…(country,time,session)
                              │       userLogin  = package-{hash}-user-{providerUsername}
                              │       userPass   = generatePasswordV2(...)
                              │  3. NodeService.createProxy() ─POST /add-port─▶ ГЕЙТВЕЙ
                              ▼
                         Prisma (наша БД): Proxy{ serverHost, userPort=10000, userLogin, userPassword,
                                                  host/port/username/password = АПСТРИМ }

                ┌─────────── РАБОТА ПРОКСИ ─────────────┐
ПОЛЬЗОВАТЕЛЬ ──▶ serverHost:10000  (логин package-…, пароль …)
                              ▼
                         ГЕЙТВЕЙ (Go)
                          ├─ auth.Validate(login,pass) → LoginConfig (в памяти)
                          ├─ ConnectUpstream → CONNECT на UpstreamHost:UpstreamPort
                          │     Proxy-Authorization: Basic base64(UpstreamUser:UpstreamPass)
                          ├─ io.Copy в обе стороны через countingConn (считает байты)
                          └─ каждые 5с: POST /api/proxy-node/traffic в CORE
                              ▼
                         АПСТРИМ (eu-isp.flashproxy.io / beta / lite / mango)
```

## 0.4. ГЕЙТВЕЙ (Go) — как он работает

Файлы: `proxy-server-code/src/proxy-agent/`.

### 0.4.1. Главное, что нужно понять

**Гейтвей — универсальный релей. Он НЕ знает про типы прокси и НЕ собирает
upstream-строки.** Он просто хранит на каждый логин запись `LoginConfig`:

```go
// auth.go
type LoginConfig struct {
    Login        string // логин клиента (наш): package-…-user-…
    Password     string // пароль клиента (наш)
    Port         int    // порт гейтвея (для отчёта по трафику)
    UserID       string
    UpstreamHost string // АПСТРИМ host  (eu-isp.flashproxy.io)
    UpstreamPort int    // АПСТРИМ port  (30)
    UpstreamUser string // АПСТРИМ user  ← СЮДА кладём ВСЮ строку с параметрами
    UpstreamPass string // АПСТРИМ pass  (o18geslcqi)
    Blocked      bool
}
```

> **КЛЮЧЕВОЙ ВЫВОД:** вся «магия» формата апстрима (country / time / session /
> мультигео) собирается на **бэкенде** и кладётся в `UpstreamUser`. Гейтвей
> вставляет её в апстрим как есть. Менять Go-код для новых типов **не нужно**.

### 0.4.2. Жизненный цикл соединения

1. `proxy_listener.go` — `Accept()` → `DetectAndDispatch()`.
2. `protocol_detector.go` — первый байт `0x05` → SOCKS5 (`socks5_handler.go`), иначе HTTP CONNECT (`http_connect_handler.go`).
3. Парсинг логина/пароля клиента (SOCKS5 user/pass auth или `Proxy-Authorization: Basic`).
4. `auth.Validate(login, password)` → `*LoginConfig` или `nil` (отказ).
5. `upstream.go` `ConnectUpstream(cfg, host, port)`:
   - если `UpstreamHost == ""` → DIRECT (без апстрима);
   - иначе TCP на `UpstreamHost:UpstreamPort`, шлёт
     `CONNECT target HTTP/1.1` + `Proxy-Authorization: Basic base64(UpstreamUser ":" UpstreamPass)`,
     ждёт `2xx`.
6. Двусторонний `io.Copy` через `countingConn`/`countingReader` — считает байты.

### 0.4.3. Подсчёт трафика (`traffic_tracker.go`)

- `countingConn.Read()` на каждое чтение делает `tracker.AddBytes(login, dir, n)` (atomic).
- В памяти `map[login]{bytesIn,bytesOut}`. **Локальной БД нет.**
- Каждые **5 секунд** `sendBatch()` считает дельту и шлёт в CORE:
  ```
  POST {core-url}/api/proxy-node/traffic
  { "server_id": "...", "logs": [ { "user": login, "port": …, "in_bytes": Δ, "out_bytes": Δ } ], ... }
  ```
- CORE по `user`(=логин) находит `userPackage` и пишет в `TrafficLog` (`inBytes/outBytes` по часам) → списывает баланс.

### 0.4.4. Блокировка при исчерпании трафика

- CORE считает остаток (баланс − сумма `TrafficLog`). Когда 0 → `POST /block-login {login}`.
- Гейтвей (`api_server.go` → `auth.SetBlocked(login,true)` + `connMgr.CloseAll(login)`):
  ставит `Blocked=true` и **рвёт все активные коннекты** этого логина. Новые — отвергает на auth.
- Пополнили баланс → `POST /add-port` (он сбрасывает `Blocked=false`) или `/sync_active_ports`.

### 0.4.5. API гейтвея (всё, кроме `/test-proxy`, требует `Authorization: Bearer {auth-token}`)

| Метод | Назначение |
|------|-----------|
| `GET /health` | список активных логинов |
| `POST /add-port` | добавить/обновить один логин (`{login,password,port,user_id,proxy_host,proxy_port,proxy_username,proxy_password}`) |
| `POST /add-ports` | то же пачкой |
| `POST /sync_active_ports` | **заменить весь реестр** (периодическая синхронизация из CORE) |
| `POST /block-login` | заблокировать логин + порвать коннекты |
| `POST /stop` | сейчас no-op |
| `GET/POST /test-proxy` | проверка логина без авторизации (CONNECT к httpbin) |

### 0.4.6. Запуск

```bash
./proxy-agent -core-url=http://core:3000 -auth-token=SECRET \
              -proxy-port=10000 -api-port=808 -server-id=gateway-eu-1
```

## 0.5. БЭКЕНД — как генерится прокси

### 0.5.1. Типы прокси (Prisma enum)

`backend/prisma/schema/proxy.prisma` и `package.prisma`:

```prisma
enum ProxyType {           // и точно такой же PackageType
  RESIDENT
  RESIDENT_PREMIUM      // Mango  (СЕЙЧАС прямой API → ВЕРНУТЬ на гейтвей, спринт 1)
  MOBILE                // ProxyEmpire (НЕ трогаем)
  MOBILE_GB             // FlashProxy mobile (через гейтвей)
  IPV6_GB               // ISP/Proxy922 (через гейтвей, USE_NODE_GATEWAY=true)
  PREMIUM_RESIDENTIAL   // ProxyEmpire (НЕ трогаем)
}
```

Новые типы (спринты 2–3) добавляем сюда: `ISP_USA`, `ISP_EU`, `RESIDENTIAL_LITE`.

### 0.5.2. Провайдеры (`backend/src/proxy/providers/services/`)

Каждый провайдер = класс с методом `createProxy(...)`, который возвращает
`{ host, port, username, password }` **апстрима**. Уже есть:

- `mango-proxy.provider.ts` — Mango;
- `proxy-empire.provider.ts` — ProxyEmpire (не трогаем);
- `mobile-gb.provider.ts` — FlashProxy mobile (хороший образец строки апстрима);
- `proxy-922.provider.ts` — ISP/IPv6 через гейтвей.

`mobile-gb.provider.ts` — **эталон формата для flashproxy**:
```ts
username = `${base}-country-${iso}-mobile-true-package-mobile-time-${min}-session-${id}`;
```
Для новых типов делаем такие же билдеры (см. спринты 2–3).

### 0.5.3. Что отдаём пользователю (через гейтвей)

`backend/src/package/package.service.ts` (~691–826) + `shared/utils/hash-credentials.ts`:

```ts
// логин клиента (наш гейтвей):
buildProxyLogin(packageId, providerUsername)
  → `package-${sha256(packageId).slice(0,8)}-user-${providerUsername}`
// пароль клиента: generatePasswordV2(packageId, suffix, iteration)  → 9 символов
const PROXY_SERVER_PORT = 10000;
```

В таблицу `Proxy` пишем оба набора:
```ts
{
  host, port, username, password,         // ← АПСТРИМ (скрыт от юзера)
  userPort: 10000, userLogin, userPassword, // ← что видит юзер
  serverHost,                              // ← IP нашего гейтвея (null = прямой провайдер)
  type, rotation, rotationInterval, country, userPackageId,
}
```
Затем `NodeService.createProxy()` (`backend/src/node/node.service.ts`) шлёт на гейтвей
`POST /add-port`, где `proxy_username` = **полная upstream-строка с параметрами**, `proxy_password` = пароль апстрима.

> `serverHost != null` ⇒ прокси идёт через гейтвей (наши типы и Mango-после-возврата).
> `serverHost == null` ⇒ прямой провайдер (ProxyEmpire — не трогаем).

### 0.5.4. Ротация

`ProxyRotation { AUTO | BY_REQUEST | BY_TIME }`, `rotationInterval` (минуты), `sessionId`.
- **BY_REQUEST** — ротация на каждый запрос, в upstream-строке только `country-XX`.
- **BY_TIME** — в строке `…-time-{минуты}-session-{8 симв}`. SESSION_ID генерим у себя.
- **Лимит времени из ТЗ: 1–1440 минут.** Больше — ошибка валидации.

## 0.6. Где сейчас «прямой API» (это и есть источник проблем)

`mango-proxy.provider.ts`:
- `@OnEvent('proxy.create_account')` → `POST /create_user`, `/add_proxy_account` (создание суб-аккаунта);
- `@OnEvent('user.distribute_traffic')` → **`POST /add_user_flow`** (доливка трафика на суб-аккаунт) — **блокирующий, медленный**;
- `@Cron(EVERY_MINUTE) updateUserBalances()` → `POST /user_info` (тянет остаток с апстрима).

`proxy-empire.provider.ts` (НЕ трогаем по ТЗ, но знать полезно):
- `addSubUserBandwidth()` → `PUT /subusers/:email` (доливка ГБ).

Эти синхронные вызовы при покупке/триале и десинхрон баланса по снапшотам
(`proxyEmpireResiUsedSnapshot`, …) — корень проблем 7.3, 8.1, 8.2 (см. спринт 1).

## 0.7. Заготовка под IPv4 / IPv6 (аренда на время, спринт 4 — НЕ реализуем сейчас)

ТЗ просит только заложить архитектуру. Рекомендуемая структура БД (миграцию можно
сделать заранее, бизнес-логику — позже):

```prisma
model RentedIp {
  id            String   @id @default(cuid())
  userId        String
  user          User     @relation(fields: [userId], references: [id])
  family        IpFamily            // IPV4 | IPV6
  ip            String              // выданный IP
  upstreamRef   String?             // как смапить на апстрим/порт
  rentedAt      DateTime @default(now())
  expiresAt     DateTime            // срок аренды
  autoRenew     Boolean  @default(false)
  notified3d    Boolean  @default(false)  // отправлено ли уведомление за 3 дня
  replaceCount  Int      @default(0)      // сколько раз меняли (бан) — лимит
  status        RentedIpStatus @default(ACTIVE)
}
enum IpFamily { IPV4 IPV6 }
enum RentedIpStatus { ACTIVE EXPIRED REPLACED }
```
Учесть: автопродление, уведомление за 3 дня (крон), выгрузка списка в `.txt`,
замена IP при бане с лимитом. Биллинг — по IP×период, не по ГБ.
